# Pattern: secret-store changes go through infrastructure as code

**Problem.** Secrets added or changed by hand in the secret store (a `vault kv put` from a
laptop, a click in a web UI) leave no review, no history and no way to rebuild the store. The next
agent or human cannot tell which secrets exist, who uses them, or why one changed.

**Pattern.** Every change to the secret store (paths, policies, roles, auth methods and the
secrets' existence) is code in the infra repo, applied by the IaC tool. Example: Vault managed
through Terraform (`vault_kv_secret_v2`, `vault_policy`, `vault_kubernetes_auth_backend_role` in
`infra/terraform`). In plain words: the repo says what the store must contain; `terraform plan`
shows the difference; `terraform apply` makes it so.

- **Values never land in git.** The code declares the secret and where its value comes from:
  generated by Terraform (`random_password`), read from an input the owner types at apply time,
  or created empty for the owner to fill. The state file then holds values: keep it in a private,
  encrypted backend (an S3-compatible bucket the owner controls), never in the repo.
- **Agents write the PR, the owner applies.** Agents usually have no backend or store
  credentials. They open the PR with the plan they expect and hand the owner a ready-to-run
  prompt or command for `terraform plan` and `apply` on the owner's machine.
- **No hand edits.** A secret found only in the store, not in code, is imported (`terraform
  import`) or recreated through code, then the manual path is closed.
- Rotations follow the same path: change the generator or the input, plan, apply, restart the
  consumers.

Anti-pattern seen: secrets put by hand in Vault during an incident were missing from the code
and the next rebuild dropped them.
